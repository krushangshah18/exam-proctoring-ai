3.1 Functional Analysis

The proposed system is an AI-based online examination proctoring platform designed to support secure exam conduction, identity-aware student participation, continuous monitoring, and post-exam administrative review. The application is implemented as a full-stack system with a Next.js frontend, a FastAPI backend, PostgreSQL for persistent records, Redis for runtime support, and a dedicated AI proctoring engine that performs object detection, gaze analysis, liveness estimation, audio correlation, and risk scoring. The platform supports three real operational roles, namely student, exam administrator, and system administrator, and each role is given controlled access according to its responsibility in the examination lifecycle.

From the student perspective, the system begins with account registration that includes selfie upload and face verification. The registration flow stores the student profile, creates a face embedding, and ensures that only a valid single face is accepted. During login, the system performs credential verification and device-aware authentication. If the device is unknown, an OTP-based verification step is enforced before access tokens are issued. This provides a layered access-control model in which both account ownership and device trust are considered before a student is allowed to enter the protected examination area.

The pre-exam stage is functionally important because the system does not directly allow a student to begin writing the exam after login. The student first enters an exam-specific flow where the application checks exam availability, invite validity, late-join policy, session state, and trusted device status. In addition, the student must complete environment checks such as face verification against the registered profile and prohibited-object checking using image analysis. This prevents a candidate from starting the exam under invalid identity conditions, from an untrusted device, or in an environment that already violates exam rules.

Once the student clears the pre-exam stage, the backend creates or reactivates an exam session. The session model stores the current state of participation, including whether the session is newly created, active, disconnected, ended, or terminated. It also stores device fingerprint, start and end timestamps, current risk score, termination reason, and fields related to the AI engine connection. After the session becomes active, the frontend establishes WebRTC communication for live proctoring. This integration allows the system to monitor the student continuously while the exam is in progress.

The monitoring flow is not a simple camera stream. The dedicated AI engine maintains per-candidate session state and processes candidate media using a coordinated multi-user architecture. It receives video and audio streams, maintains the latest media for each active candidate, and performs shared batch inference for object detection while keeping per-session state for gaze, liveness, audio activity, risk accumulation, alerts, and proof generation. This architecture enables the system to support multiple students on the same server without mixing user state. Alerts generated by the engine are streamed back to the application and are used to update session risk, terminate sessions when necessary, and provide live monitoring information to the student and the exam administrator.

On the administrative side, the exam administrator can create, edit, and cancel exams; configure detection toggles; invite students; monitor active sessions; inspect live proctoring feeds; review resume requests; and access completed reports. The system administrator has a different scope of responsibility. This role can review admin applications, manage platform-wide engine settings, and review user and trusted-device information. Therefore, the system separates academic supervision, platform governance, and student participation into clearly bounded functional layers rather than combining all controls under a single account type.

The overall functional behavior of the system can be summarized in five stages: user onboarding, secure authentication, pre-exam validation, active proctored examination, and post-exam review and recovery. This staged design improves fairness and reliability because the system checks readiness before the exam starts, monitors continuously during the exam, and still preserves post-exam evidence, audit information, and appeal workflows for review after disruptions or terminations.

3.2 Security and Compliance Analysis

Security is a foundational requirement of the proposed system because the platform handles student identity, face embeddings, device trust, exam schedules, and live monitoring data. The project implements security not as a single feature but as a collection of controls across authentication, authorization, device binding, session integrity, communication security, and auditability. These controls are visible in both the backend business logic and the frontend examination workflow.

At the authentication layer, the backend uses hashed passwords, access tokens, refresh tokens, and role-based authorization. Distinct roles are assigned for student, exam administrator, and system administrator, and protected routes validate both user identity and role eligibility before sensitive operations are allowed. This prevents students from accessing administrative interfaces and ensures that system-wide settings remain under system administrator control only. In addition, account lock logic is present for repeated failed login attempts, reducing brute-force login risk.

Device trust is a major security feature of this system. During login, the platform calculates a device fingerprint and checks whether the device is already trusted for the user. If the device is new, the login flow pauses and an OTP is sent to the registered email address. Only after OTP verification is the device promoted to trusted status. The system can also revoke older devices and their associated refresh tokens. During the exam flow, session start is additionally bound to the trusted device, and concurrent active exam usage from another device is blocked. This significantly reduces the risk of account sharing, remote session hijacking, and parallel exam access.

Identity compliance is further strengthened through selfie-based face verification. Student registration stores a face embedding, and later profile updates and pre-exam face checks compare newly captured embeddings against the stored reference. This reduces impersonation risk and provides a stronger assurance that the person taking the exam is the same person who registered on the platform. Because the system also validates that exactly one face is present during registration and pre-exam checks, it avoids accepting ambiguous or multi-person images.

Session-level security is enforced using heartbeats, disconnect handling, and controlled resume logic. Active sessions periodically update heartbeat information. If the heartbeat becomes stale, the backend marks the session as disconnected, and after a configured timeout the system may terminate the session automatically. However, the design is not blindly punitive. It supports resume requests, late-join review, and administrative approval with optional time extension. This balance is important from a compliance perspective because secure examination systems must preserve integrity without being unfair in the presence of real network disruptions.

Communication security is also addressed in the implementation. The backend applies CORS restrictions, secure response headers, content security policy settings, and token-based access control. Student media is transmitted through a controlled proctoring flow in which the backend proxies signaling to the AI engine rather than exposing the engine directly as a public interface for the browser. This reduces direct attack surface and keeps engine-specific connection information under backend control.

Finally, the project maintains strong auditability and data accountability. Audit logs are written for sensitive actions such as account locking, profile updates, admin approvals, and device revocations. Session records store termination reasons, termination source, risk score, and timing information. Resume requests preserve review decisions and notes. These records support transparency, administrative review, dispute handling, and future governance requirements. Therefore, the system is compliant in spirit with the needs of controlled digital examination environments: authenticated access, traceable actions, controlled identity verification, session accountability, and reviewable evidence.

3.3 Functional Requirements

The following functional requirements are derived directly from the implemented student flows, administrative controls, authentication logic, and AI proctoring pipeline present in the project. The requirements are organized role-wise so that the behavior expected from each user category is clearly specified.

1. Student:

R1.1: Register Student Account

Description:

The student can create a new account by providing name, email, password, consent, and a selfie image. The system validates the form data, checks that the uploaded image contains exactly one face, generates the face embedding, and creates the student account.

Input:

Email, full name, password, consent flag, and selfie image.

Output:

Successful registration message or validation error message if the image or form data is invalid.

R1.2: Log In with Device Verification

Description:

The student can log into the system using registered credentials. If the login originates from a trusted device, the system issues access and refresh tokens directly. If the device is new, the system creates a pending device entry and sends an OTP for device verification before granting access.

Input:

Email, password, browser/device fingerprint, and OTP in case of a new device.

Output:

Access token and refresh token for a verified device, or OTP verification message for a new device.

R1.3: Manage Student Profile

Description:

The student can view personal profile information, update the basic profile, and update the profile image. While updating the profile image, the system performs single-face validation and verifies that the new selfie belongs to the same person as the stored identity.

Input:

Updated full name or new selfie image.

Output:

Updated profile information or an error indicating invalid image, identity mismatch, cooldown restriction, or active-exam restriction.

R1.4: View Exam Dashboard and History

Description:

The student can view upcoming exams, exam history, session status, session summaries, and exam-specific information before entering the exam flow. The system retrieves this information from invite records, exam records, and session records.

Input:

Authenticated student identity and selected exam identifier.

Output:

List of upcoming exams, past exams, current exam status, and session summary details.

R1.5: Perform Pre-Exam Checks

Description:

Before starting the exam, the student can perform system and environment readiness checks. These checks include engine availability, face verification against the registered profile, and prohibited-object detection to confirm that the candidate is ready to start the exam under valid conditions.

Input:

Exam identifier, webcam image for face verification, and webcam image for object checking.

Output:

Readiness result showing whether the student can proceed, along with any issue messages for identity or environment problems.

R1.6: Start or Reconnect Proctored Exam Session

Description:

The student can start a new exam session or reconnect to a disconnected one. The system validates exam availability, late-join rules, appeal state, and trusted-device status before creating or reactivating the session and binding it to the current device.

Input:

Exam identifier, authenticated student identity, and trusted device fingerprint.

Output:

Session identifier and start success message, reconnect success message, or denial message when the session cannot be started.

R1.7: Connect to Live Proctoring

Description:

During an active exam, the student client can connect to the AI proctoring engine through backend-proxied WebRTC signaling. The system allocates an available engine, forwards offer and ICE data, and establishes the live monitoring session.

Input:

Exam identifier, SDP offer, ICE candidates, camera stream, and microphone stream.

Output:

WebRTC answer, live proctoring connection, and active risk-event stream.

R1.8: Participate in Active Exam Session

Description:

The student can continue the exam while the system maintains the session using heartbeat updates, receives proctor alerts, and reports client-side focus violations such as tab-switch events. The system updates session state and may terminate the session if policy violations become severe.

Input:

Heartbeat signals, tab-switch or focus-violation events, and ongoing audio-video stream data.

Output:

Alive status, warning alerts, risk updates, termination notice, or reconnect redirection when needed.

R1.9: Submit and End Exam Session

Description:

The student can submit the exam and close the active session. The system marks the session as ended, updates the invite as used, and attempts to fetch the final report and final risk score from the AI engine.

Input:

Active exam session and final submit action.

Output:

Exam ended message, session identifier, final status, and completion summary for the student.

R1.10: Appeal Late Join or Terminated Session

Description:

The student can file an appeal if a late join requires approval or if the session is terminated and the rules still allow re-entry. The student can also dismiss the appeal flow when choosing not to continue.

Input:

Exam identifier and written appeal reason or dismiss action.

Output:

Appeal submission confirmation, appeal state, or dismissal confirmation.

2. Exam Admin:

R2.1: Log In as Exam Administrator

Description:

The exam administrator can log in using authenticated credentials and trusted-device verification in the same secured authentication framework used by the platform.

Input:

Email, password, device fingerprint, and OTP when needed.

Output:

Authenticated admin session with access to the exam administration dashboard.

R2.2: Create Exam and Send Invites

Description:

The exam administrator can create an exam by defining title, schedule, duration, late-join policy, detection configuration, and list of invited students. The system stores the exam, generates invite tokens, and sends invitation emails.

Input:

Exam title, exam mode, start window, end window, duration, late-join settings, detection toggles, and invitee email list.

Output:

Created exam record, generated invites, and invite delivery notifications.

R2.3: Update or Cancel Exam

Description:

The exam administrator can update editable exam details before the exam begins and can cancel an exam when necessary. On updates or cancellation, the system sends appropriate notifications to the affected students.

Input:

Exam identifier and modified schedule or control parameters, or cancellation action.

Output:

Updated exam details or cancelled exam status, along with student notification effects.

R2.4: View Dashboard Metrics and Session Lists

Description:

The exam administrator can view exam-level dashboard statistics, live-session counts, student session states, and pending appeal information for exams managed by that administrator.

Input:

Authenticated exam administrator identity and selected dashboard filters or exam identifiers.

Output:

Dashboard metrics, session lists, pending-appeal lists, and exam-level status information.

R2.5: Monitor Live Exam Sessions

Description:

The exam administrator can monitor active student sessions by requesting live frames, subscribing to live event streams, and enabling or disabling debug overlays for diagnostic viewing.

Input:

Exam identifier, session identifier, and debug-mode control action.

Output:

Live frame feed, live event updates, and debug-mode status response.

R2.6: Review Resume Requests

Description:

The exam administrator can inspect student resume requests for late join or terminated sessions, review the reason, and decide whether to approve or deny the request, optionally granting a time extension.

Input:

Resume request identifier, review decision, review note, and optional extension value.

Output:

Updated request status, updated session state, and notification event for the affected student session.

R2.7: View Reports and Completed Session Details

Description:

The exam administrator can review completed sessions, final risk scores, termination reasons, and report details collected during or after the proctored exam.

Input:

Exam identifier, session identifier, and report query action.

Output:

Report details, session history, final risk information, and related review data.

3. System Admin:

R3.1: Review Admin Applications

Description:

The system administrator can view submitted admin applications and approve or reject them. Approval may create a new admin account, promote an existing student account, or reactivate a deleted account depending on the current state of the applicant email.

Input:

Application identifier, approval or rejection decision, and optional review note.

Output:

Updated application status, created or updated admin account, and notification email to the applicant.

R3.2: Manage Engine and Detection Settings

Description:

The system administrator can view and update platform-wide AI engine settings, including thresholds, detection sensitivity parameters, and scoring-related values used to build engine configuration for proctored exams.

Input:

Engine threshold values, scoring values, and detection-related configuration fields.

Output:

Saved engine settings and updated configuration state for future proctoring sessions.

R3.3: Review Users and Trusted Devices

Description:

The system administrator can inspect user and device-related information for governance and security control. This includes reviewing trusted-device records and related administrative account control information.

Input:

User identifier, device listing request, or device management action.

Output:

User-device information, trust status visibility, and updated device-control state where applicable.

3.4 Non-Functional Requirements

In addition to the functional capabilities described above, the project requires several non-functional properties so that the platform remains usable, secure, and scalable in real examination scenarios. These requirements are directly motivated by the architecture and implementation choices used in the project.

Requirement ID Non-Functional Requirement
NFR-1 Security: All protected operations shall require authenticated access, role validation, and secure token handling. Sensitive actions such as login, device verification, and account recovery shall be rate-limited or otherwise protected against abuse.
NFR-2 Reliability: The system shall handle disconnects, stale sessions, and recovery flows gracefully through heartbeat tracking, disconnected-state management, and appeal or resume handling.
NFR-3 Performance: The AI monitoring engine shall process active sessions in coordinated ticks and shall use shared batch inference to support multiple concurrent students efficiently.
NFR-4 Scalability: The architecture shall support multi-user monitoring through sessionized state management, engine-container allocation, and independent handling of student sessions.
NFR-5 Usability: Student-facing pages shall guide the user through registration, device verification, pre-exam checks, active exam participation, and completion or termination outcomes using clear route-based flows.
NFR-6 Maintainability: The codebase shall remain modular, with clear separation between frontend, backend API, database models, and AI engine components so that future enhancements can be introduced without rewriting the whole system.
NFR-7 Auditability: The system shall preserve logs, session states, risk summaries, and review records so that administrative decisions and exam outcomes can be traced later.
NFR-8 Availability: The platform shall remain operational even when some users disconnect temporarily, and it shall clearly communicate whether the system, exam, or AI engine is available before exam start.
NFR-9 Consistency: The system shall use centralized database-backed records for users, exams, devices, sessions, resume requests, and engine settings so that all actors observe the same state.
NFR-10 Portability: The software stack shall be deployable in a standard web environment using modern browsers for the frontend and Python-based runtime support for backend and engine services.

3.5 Hardware Requirements

The hardware requirements of the proposed system depend on the role and deployment location. Since the project includes a web frontend, a backend API, and a separate AI engine, the hardware needs are different for students, administrators, and the proctoring server. The following configuration is based on the actual implementation and runtime dependencies of the project.

Component Minimum Practical Requirement Purpose in the System
Student Device Laptop or desktop with modern browser, webcam, microphone, stable internet connection, and enough processing power to capture live audio/video streams Required for registration selfie, device-verified login, pre-exam checks, live exam participation, WebRTC media transmission, and exam submission
Exam Administrator Device Laptop or desktop with modern browser and reliable internet connection Used for exam creation, session monitoring, appeal review, report viewing, and dashboard access
System Administrator Device Laptop or desktop with modern browser and reliable internet connection Used for system-level settings, admin-application review, and platform administration
Backend Application Server Multi-core CPU, adequate RAM, and storage sufficient for PostgreSQL, Redis, report metadata, and application runtime Runs FastAPI backend, persistent business logic, authentication, exam/session workflows, and database integration
Database and Cache Host PostgreSQL-capable storage environment and Redis-capable memory support Stores users, exams, invites, sessions, trusted devices, audit data, and supports low-latency session-related operations
AI Proctoring Engine Host CUDA-capable NVIDIA GPU, sufficient VRAM, CPU, and memory to run YOLO, MediaPipe, and WebRTC processing Required because the object detection engine explicitly expects GPU-backed execution for real-time multi-user proctoring

From an academic deployment perspective, the most important hardware distinction is that the backend server and the AI engine are separated. The backend can operate as a standard web service, but the AI engine has stricter computational requirements because it performs live object detection, MediaPipe-based face analysis, audio processing, and concurrent multi-session coordination. Therefore, student and admin devices may remain lightweight browser-based clients, while the monitoring engine requires stronger dedicated hardware for dependable real-time performance.
